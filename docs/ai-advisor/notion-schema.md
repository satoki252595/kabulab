## 4. 自動化が触るプロパティ（名前は完全一致。全文は schema-spec）

### 4.1 日次タスク（`TASKS`）

人が書く: `目的`（必須）、`対象銘柄`（企業分析・投資判断で必須）、`利用者`（任意。空なら `作成者`）、`対象日`（任意）、`ルール`（任意・明示時）、`観点`（任意・絞る時）、`繰り返し`。
AI が書く: `タスク名`、`対象日`（補完）、`観点`、`状態`、`完了観点`、`適用ルール`、`専属エキスパート`、`変化`、`要約`、`実行メモ`、本文。
自動: `作成者` `作成日時` `判断待ち`（rollup） `判断` `連鎖元判断` `振り返り`（逆側）。

本文の構造: `作成中（k/m 観点）` → 頭（`@利用者` 判断待ち／適用ルール／制約との一致／変化）→ `## 観点: <観点名>` ×N（要約／寄与／根拠／確認不能）→ `## 統合` → 尾（確認不能の一覧／出典一覧／免責）。

### 4.2 専属エキスパート（`EXPERTS`）

読む: `名前` `オーナー` `状態` `投資期間` `1銘柄あたり金額` `許容損失` `見ない領域`（制約4項目） `ウォッチ上限`（空なら 10） `低確信度のサイズ`（空なら「通常の半分」）。
書く: `直近の学び`。`オーナー` 空の行はワークスペース共通行（タスクには使わない）。

### 4.3 ルール（`RULES`）

読む: `ルールID` `オーナー` `専属エキスパート` `対象目的` `対象観点` `バージョン` `状態` `前バージョン` `発効日`、本文（共通節と `## 観点: X` 節だけ）。
本文見出し: `## 1. 選定基準（スクリーニング）` `## 2. 除外・見ない領域` `## 3. 企業分析で必ず見る項目` `## 4. IF-THEN（買う条件 / 見送り条件 / 破綻条件）` `## 5. サイズとRR` `## 6. 再提示の間隔と次回確認の既定` `## 7. 振り返りの見方` `## 8. 変更理由` `## 観点: <観点名>`。
書く: 草案の新行（`ルールID` `オーナー` `専属エキスパート` `対象目的` `対象観点` `バージョン` `状態=草案` `前バージョン` `根拠振り返り` `変更要約` 本文）、同系旧 `発効` の `状態=失効`＋`変更要約` 末尾、`発効日` 補完。

### 4.4 分析観点（`AXES`）— 読むだけ

`観点名` `目的` `順序` `有効` `オーナー` `専属エキスパート` `問い` `参照資産` `スライス`（`銘柄=対象|全体 / 期間=… / 項目=… / 件数=… / クエリ=… / 節=…`） `取得上限`（既定 30・最大 100） `重さ` `判断材料テンプレ` `学び材料への出力`、本文（300 字: 問い／見る点／寄与の判定基準）。共通観点の既定行は schema-spec §7。

### 4.5 参照資産（`ASSETS`）— 読むだけ

`名称` `種別` `パス・URL`（`{code}` を証券コードに置換。`…` は `https://kabulab-cf.satoki252595.workers.dev`） `提供データ` `用途` `ライセンス` `更新` `必要Secret`（名前だけ） `状態` `オーナー`。既定行は schema-spec §8.4（`docs/ai-advisor/reference-data.md` §2 に転記）。

### 4.6 銘柄（`STOCKS`）

読む: `銘柄名` `証券コード`、本文 `## 事実台帳` の最新 30 行。
書く: 新行（`銘柄名` `証券コード` `参照URL`）、正式名・コードの正規化、本文末尾への追記 `- [基準日 YYYY-MM-DD] 種別 | 内容 | 出典URL | 品質 | 観点名`（種別: 事実／計算／推論／確認不能、品質: 正常／要確認／欠損）。`市場` は JPX 由来のため書かない。

### 4.7 判断（`DECISIONS`）

AI が骨格を作る（§1 の列）。人は `最終判断`（と任意で `判断メモ`）だけ触る。`判断日` は最終判断を初めて検知した日（夕振り返りが刻む。以後不変）。`次タスク` は連鎖・再確認起票の二重防止。`追跡メモ` は振り返りごとに上書き。`最終更新者` は夕の検査で見る。本文は書かない。

### 4.8 振り返り（`REVIEWS`）

`振り返りID` `対象日` `利用者` `専属エキスパート` `対象タスク` `対象判断` `関連観点` `ルール遵守` `見落とし` `学び` `ルール対応` `草案ルール` `未判断件数` `小サンプル`、本文（見出し 1〜8 は automation-spec §5）。

## 5. 文脈予算（automation-spec §1。全自動化共通）

| 単位 | 上限 |
| --- | --- |
| 1 観点の取得件数 | `分析観点.取得上限`（既定 30、最大 100）。クエリの `limit`／`n`、無ければ `jq` で先頭／末尾 N 件 |
| 1 観点の項目 | `スライス` の `項目=` のみ（≤12）。`jq` で射影してから読む |
| 1 観点の期間 | `スライス` の `期間=`（日足は末尾 120 行、需給は `n=8`、開示は `pubdate` で絞る） |
| 1 観点の文書 | 2（`重`）。`節=` の見出しだけ抜く。全文を読まない |
| 1 観点の出力 | 要約 ≤600 字、寄与 1 語、根拠 3 行、確認不能。書いたら生データを捨てる |
| 統合の入力 | 本文の観点の節（要約・寄与）だけ。再取得しない |
| Notion の読み | 専属: 必要列のみ／ルール: 共通節＋`## 観点: X` 節／観点本文 300 字／銘柄本文 最新 30 行／前回タスク 統合節のみ／過去判断 20 行（同じ利用者×銘柄、判断日降順）。fetch は対象ページだけ。DB クエリはフィルタ付き（状態・対象日・利用者）＋`limit` |
| 1 ランの観点数 | `軽` 8／タスク、`重` 1／タスク。超えたら `実行中`＋`完了観点` で次ランに再開 |
| 1 ランの行数 | 朝レポート: タスク 10 行／夕振り返り: 利用者 10 人・追跡判断 30 行／人／随時実行: Webhook 1 行・ポーリング 5 行 |
| ロック | `状態=実行中`＋`実行メモ` の実行ID。60 分進捗なしは引き継ぎ |

## 6. REST フォールバック（MCP が使えないときだけ）

```bash
test -n "$NOTION_TOKEN" && echo "NOTION_TOKEN: set" || echo "NOTION_TOKEN: missing"   # 値は表示しない

curl -sS -X POST "https://api.notion.com/v1/data_sources/${DATA_SOURCE_ID}/query" \
  -H "Authorization: Bearer ${NOTION_TOKEN}" -H "Notion-Version: 2025-09-03" -H "Content-Type: application/json" \
  --data '{"filter":{"property":"状態","status":{"equals":"未着手"}},"page_size":10}'
```
