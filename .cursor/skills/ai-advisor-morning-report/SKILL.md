# 朝レポート（日次タスク → 観点の節 → 統合 → 判断行）

正本は Project の `internal/automation-spec.md`（GitHub 版が入れば `docs/ai-advisor/plan-and-design.md`）。この文書はそれを **手順どおりに実行するための操作手引き** で、矛盾したら正本が勝つ。参照する周辺文書:

- `docs/ai-advisor/guardrails.md` — 書いてはいけないもの・自己検査（automation-spec §7）
- `docs/ai-advisor/notion-schema.md` — 8DB の名前・プロパティ名・状態値・保存ビュー・文脈予算（schema-spec の要約）。DB は **名前で解決**、ID は保険
- `docs/ai-advisor/reference-data.md` — 参照資産のライセンス階層と、観点 → `curl`＋`jq` の取得形（automation-spec §6）
- `references/jp-holidays.md` — 営業日判定の祝日リスト

## 0. 役割と前提（毎回）

- 役割: 自己成長するAI投資家アドバイザーの自動化。**投資助言をしない。人の最終判断を代行しない。** 判断材料（本文）と学び材料（`判断` 行の骨格）を書くまで。
- 固定値: 親ページ `https://app.notion.com/p/3dad74ff84cd80c4956feaf9255de7e1`。8DB（`専属エキスパート` `ルール` `分析観点` `参照資産` `銘柄` `日次タスク` `判断` `振り返り`）は親ページの子を **名前で解決**（`notion-fetch` で親ページ → 子データベース一覧 → 名前一致 → 各 DB を `fetch` してデータソース URL とプロパティ名を確認）。`notion-schema.md` §1・§2 の ID・保存ビュー URL（2026-09-15 照合済み）と一致することを確かめ、食い違えば **名前解決の結果を優先** して実行サマリーに書く。
- **状態の解決（防御）**: `日次タスク.状態` は仕様名（`未着手` `不足` / `実行中` / `レポート済`）を第一に使い、その選択肢が無いときは **グループ** で解決する — In progress グループの唯一の選択肢（現状 `進行中`）を「実行中」、Complete グループの唯一の選択肢（現状 `完了`）を「レポート済」として読み書きする。`不足` が無いときは **`未着手` のまま `実行メモ` の先頭に `不足:<コード>`** を書く（読むときは `未着手` かつ `実行メモ` が `不足:` で始まる行を「不足」とみなす）。rows モードのフィルタは `status_is` の `is_group`（`to_do` / `in_progress` / `complete`）を使う。どの名前で解決したかを実行サマリーに 1 行書く（`notion-schema.md` §3.1）。
- 時刻: JST。実行ID `YYYYMMDD-HHMM-朝レポート`（`TZ=Asia/Tokyo date +%Y%m%d-%H%M`）。
- 営業日: 月〜金 かつ `references/jp-holidays.md` の祝日・12/31〜1/3 でない日。判定できない日は営業日とみなす。
- 無人実行: 人に質問しない。迷えば `確認不能`、起動条件を満たさなければ `不足`（§2）。
- 同時実行: この自動化は同時 1 インスタンス。行のロックは `状態=実行中`＋`実行メモ` の実行ID。
- **文脈予算**（automation-spec §1）: 全表を読まない。観点ごとに `分析観点.取得上限`（既定 30、最大 100）・`スライス` の `項目=`（≤12 列）・`期間=` に切ってから読む。取得は **シェル**（`curl -sS -m 30 "<URL>" | jq -c '<射影・件数制限>'`）で行い、数 KB の結果だけを読む。`jq` が無ければ `python3 -c` で同等に射影する。1 観点の出力は 要約 ≤600 字・寄与 1 語・根拠 3 行・確認不能。書いたら生データ・一時ファイルを捨て、以後参照しない。統合は本文の観点の節だけを入力にする。
- 1 ランの上限: タスク 10 行、観点 `軽` 8／タスク、`重` 1／タスク。

## 1. 起動時に読むもの（データはまだ読まない）

1. `docs/ai-advisor/guardrails.md`、`docs/ai-advisor/notion-schema.md`、`docs/ai-advisor/reference-data.md`、`references/jp-holidays.md`
2. 親ページ → 8DB の名前解決とプロパティ名の確認（`fetch` はスキーマ確認に使い、ここで行データを読まない）。名前解決できない DB があれば、書き込みをせず実行サマリーに「未解決: 〈DB名〉」と書いて終了する
3. 当日（JST）と営業日判定、実行ID

## 2. 起動条件・解決規則（automation-spec §2）

### 2.1 タスク 1 行に対する読み順

1. `日次タスク` の行（目的・対象銘柄・利用者・作成者・対象日・ルール・観点・完了観点・状態・実行メモ・繰り返し）
2. **専属**: `利用者`（空なら `作成者`）で `専属エキスパート` を `オーナー` で検索（rows モード、`limit: 1`）。`状態=運用中` でなければ不足。読む列は 制約4項目・`ウォッチ上限`（空なら 10）・`低確信度のサイズ`（空なら「通常の半分」）
3. **目的ルール**: タスクの `ルール` が指定され `状態=発効` ならそれ。空なら「`オーナー`＝利用者 かつ `対象目的` ∋ 目的 かつ `対象観点` 空 かつ `状態=発効`」を `発効日` 降順で 1 行 → 無ければ「`オーナー` 空（共通）」で同条件 1 行 → 無ければ不足 `RULE_UNRESOLVED`
4. **観点解決**: タスクの `観点` が空なら「`有効`=ON かつ `目的` ∋ 目的 かつ（`オーナー` 空 または `オーナー`＝利用者）」を `順序` 昇順（同順は共通 → 個人）。保存ビュー「自動化_有効観点」を目的で絞って読む（`page_size` は観点数上限）。結果を `観点` に書く。`完了観点` にある観点は飛ばす
5. **観点ルールと参照資産**（観点 X を回す **直前** に）: 「`対象観点` ∋ X かつ `状態=発効` かつ（`オーナー`＝利用者 または 共通）」を各 1 行（個人優先）。目的ルール本文は **共通節と `## 観点: X` 節だけ** を読む。X の `参照資産` relation の行のうち `状態=有効` かつ `必要Secret` 空 かつ（`オーナー` 空 または 利用者）だけを取得対象にし、`ライセンス` と `更新` を控える
6. 銘柄の事実台帳（`銘柄` ページ本文の **最新 30 行**）、前回タスク（同じ利用者・目的・銘柄で `レポート済` の最新 1 件。読むのは `## 統合` 節だけ）、過去判断（同じ利用者×銘柄、`判断日` 降順 20 行。列だけ）
7. 観点の切片（§0 の型で）

`適用ルール` ＝ 目的ルール 1 行 ＋ 観点ルール（各観点の分）。実行開始時に relation で固定し、以後変えない。

### 2.2 不足コード（`状態=不足` にするとき `実行メモ` に 1 行）

| コード | 意味 |
| --- | --- |
| `NO_PURPOSE` | `目的` が空 |
| `NO_STOCK` | 企業分析・投資判断で `対象銘柄` が空 |
| `STOCK_UNRESOLVED` | 銘柄名が証券コードに解決できない |
| `NO_EXPERT` | 利用者の専属行がない（このときだけ `専属エキスパート` に `状態=設定中`・`オーナー`=利用者 の行を作ってよい） |
| `EXPERT_NOT_ACTIVE` | 専属が `運用中` でない |
| `CONSTRAINT_EMPTY:<列名>` | 制約4項目（`投資期間` `1銘柄あたり金額` `許容損失` `見ない領域`）のどれかが空 |
| `RULE_UNRESOLVED` | 発効ルールが個人にも共通にもない |
| `RULE_NOT_ACTIVE` | 明示された `ルール` が発効でない |
| `NO_AXIS` | 有効な観点が 1 つもない |
| `WRITE_FAILED` | Notion 書き込みが 2 回再試行しても失敗 |

`不足` の行は毎ランで再評価し、揃っていれば `未着手` に戻して実行する（`不足` 選択肢が無い間は `実行メモ` 先頭の `不足:<コード>` を消す）。**参照資産に到達できない・フィールドが無い場合は不足にしない** — その観点の寄与を `確認不能` にして節を書き、次の観点へ進む。

銘柄名の解決: 参照資産『kabulab IR Catalog』の `name`／『kabulab 有報定量検索（推移）』の `stock.name`、無ければ『kabulab 銘柄リスト（凍結）』を `jq` で **1 件だけ** 引く（`market` は書かない）。`銘柄名` が `6098` のようにコードだけなら正式名に直し、`証券コード` を正規化する。

## 3. ルール整理（§3.0。冪等）

1. `ルール` を `状態=発効` で読む（rows モード、`limit: 100`。列: ルールID・オーナー・対象目的・対象観点・バージョン・前バージョン・発効日・作成日時）
2. `オーナー`×系（`前バージョン` を辿る）でまとめ、同系に `発効` が 2 行以上あれば、`発効日`（空なら作成日時）が最新以外を `状態=失効` にし、`変更要約` の末尾に `（自動失効 実行ID）` を付ける
3. `発効` で `発効日` が空なら当日を補完する

これ以外に `ルール.状態` を変えない（`発効`・`棄却` にしない。草案の作成は夕振り返りの仕事）。

## 4. 準備（§3.1。冪等。休場日は (a) を行わない）

| 手順 | 条件 | 書く |
| --- | --- | --- |
| (a) 繰り返し展開 | 当日が営業日。`繰り返し=毎営業日` かつ `対象日`＝前営業日 かつ `状態=レポート済` の行（rows モード・フィルタ付き）。当日分（同じ 利用者・目的・対象銘柄・ルール・観点・繰り返し）が無い | 新行: `対象日`=当日、`状態`=未着手、`タスク名` 空、`実行メモ`=`複製元:<前行URL>`、他の列は複製 |
| (b) 連鎖起票 | `判断.最終判断` ∈ {要分析, 投資判断へ進む} かつ `次タスク` 空 | 新行: `目的`=（要分析 → 企業分析、投資判断へ進む → 投資判断（売買計画））、`対象銘柄`=判断.銘柄、`利用者`=判断.利用者、`対象日`=当日。判断の `次タスク` に新行 |
| (c) 再確認起票 | `判断.最終判断` ∈ {監視, 待つ} かつ `次回確認日 ≤ 当日` かつ `次タスク` 空 | 新行: `目的`=（監視 → 企業分析、待つ → 投資判断（売買計画））。判断の `次タスク` に新行 |
| (d) 不足の再評価 | `状態=不足` の行（`不足` 選択肢が無い間は `未着手` かつ `実行メモ` が `不足:` で始まる行） | 起動条件（§2.2）が揃えば `未着手`（`実行メモ` の `不足:` を消す） |

(b)(c) の `判断` はビュー「追跡中」相当のフィルタ（`最終判断` in (要分析, 投資判断へ進む, 監視, 待つ) かつ `次タスク` 空）で `limit: 50`。

## 5. 実行（§3.2。タスクごと）

対象: 保存ビュー「自動化_実行待ち」（`notion-schema.md` §2 の URL。`mode: "view"`, `page_size: 20`）を 1 ページ目だけ読み、**自動化が自分で絞る**（ビューのフィルタに `対象日 ≤ 今日` が無いことがあるため）:

- `対象日` が空、または `対象日 ≤ 当日`（JST）の行だけ残す。`対象日 > 当日` は除く
- 状態が To-do の `未着手`（`実行メモ` が `不足:` で始まる行は除く）、または In progress（`実行中`／`進行中`）かつ `完了観点` が 1 件以上（＝再開待ち）の行だけ残す
- `タスク名` が `テンプレート｜` または `例｜` で始まる行は除く
- `対象日` 昇順、作成日時昇順に並べ、**10 行で打ち切り**（残りは実行メモに `未処理 n行`、実行サマリーに書く）

ビューが 0 件・エラーのときは rows モードで同じ条件（`status_is` `is_group: to_do` と `in_progress`、`limit: 20`）を読んで同じ絞りを行う。

1. **ロック**: `状態=実行中`（無ければ In progress グループの選択肢）、`実行メモ` の先頭に `実行ID 開始時刻`。すでに In progress で `実行メモ` の最終更新が 60 分以上前なら放棄とみなして引き継ぐ（`実行メモ` に `引き継ぎ 実行ID`。進捗があれば `完了観点` から再開）。直後に再取得して自分のロックであることを確認する。
2. **起動条件**（§2.2）。不足なら `状態=不足`（無ければ `未着手` に戻して `実行メモ` 先頭に `不足:<コード>`）と理由を書いて次の行へ。
3. **観点解決**（§2.1-4）。`観点` を書く。`適用ルール` を固定する。
4. **本文の頭**（初回のみ。`notion-update-page` `insert_content` `position: start`）:

   ```
   作成中（0/m 観点）
   @利用者（person メンション） ／ 判断待ち: 統合後に記入
   適用ルール: <ルールID v> ／ <観点ルール…>
   制約との一致: 投資期間 一致｜注意 ／ 1銘柄あたり金額 … ／ 許容損失 … ／ 見ない領域 …
   変化: （統合で確定）
   ```

5. **観点ループ**（`順序` どおり。`重` は 1 観点で打ち切り、`軽` は 8 まで。`完了観点` にある観点は飛ばす）
   1. 読む: 観点行（問い・スライス・取得上限・重さ・学び材料への出力・本文 300 字）→ 観点が指す参照資産の行（§2.1-5 の条件。`パス・URL`・`提供データ`・`ライセンス`・`更新`）→ 観点ルール → 目的ルールの `## 観点: X` 節 → 事実台帳（最新 30 行のうちこの観点に関係する行）
   2. 取得: 参照資産があれば `パス・URL` に `{code}` と `スライス` の `クエリ=` を当て、**シェル**で取得し、`項目=`・`件数=`・`期間=` に切る（`docs/ai-advisor/reference-data.md` §4 の観点別の取得形をそのまま使う）。`ライセンス` を確認し、`更新` から基準日の遅れを控える。失敗（HTTP ≠ 200、タイムアウト 30 秒、JSON 不正、期待フィールド欠落）→ 1 回だけ再試行 → それでも失敗なら寄与 `確認不能`、根拠に `到達不能 <HTTPコード>`
   3. 判定: 観点の問いに答える。寄与 ∈ `有利`／`中立`／`不利`／`確認不能`（観点本文の判定基準、観点ルールの閾値）
   4. 書く（本文の末尾に節を **追記**。`insert_content` `position: end`）:

      ```
      ## 観点: <観点名>
      要約: （≤600字。事実／計算／推論を分ける。personal-only は成立／未成立のみ）
      寄与: <有利|中立|不利|確認不能> — <理由1行>
      根拠: 参照資産『<名称>』 <URL> 取得 <YYYY-MM-DD HH:MM JST> 読んだ件数 <n>/<上限>
      確認不能: （あれば列挙。無ければ「なし」）
      ```

      見出しの `<観点名>` は `分析観点.観点名` と一字一句一致させる（振り返りが突き合わせる）。
   5. 事実台帳に追記（`銘柄` ページ本文の末尾。**commercial-ok / factual-cite の事実のみ**。書式 `- [基準日] 種別 | 内容 | 出典URL | 品質 | 観点名`）。personal-only は書かない
   6. `完了観点` に追加、`実行メモ` に `観点 k/m 完了 時刻`、本文先頭の `作成中（k/m 観点）` を更新（`update_content`）
   7. **捨てる**: 取得データと一時ファイルを消し（`rm -f /tmp/axis-*`）、以後参照しない。次の観点へ
   8. 上限（`重` 1／`軽` 8）に達したら `状態=実行中` のまま終える（次のラン＝随時実行または翌朝で再開）
6. **統合**（全観点が `完了観点` にある場合のみ）: 本文の観点の節（要約・寄与）だけを読み、目的別（§6）に `## 統合` を書く。書く前に自己検査（`guardrails.md` §8）。外部データを再取得しない
7. **判断行**（学び材料）: 既存（`元タスク`×`銘柄`）があれば作らない。`変化=なし` なら作らない。列: `判断ID`（`YYYY-MM-DD 目的 銘柄名 利用者名`）、`元タスク`、`銘柄`、`目的`、`利用者`、`専属エキスパート`、`適用ルール`、`AIの結論`、`観点別寄与`（`名:寄与／名:寄与…`）、`AIの一言`、`確信度`、`反証条件`、`次回確認日`。**`最終判断`・`判断メモ` は触らない。本文は書かない**
8. **仕上げ**: `タスク名`（`YYYY-MM-DD 目的 銘柄名`。スクリーニングは銘柄なし）、`要約`（1 行）、`変化`（§7）、`専属エキスパート`、本文先頭の `作成中` 行を外す、本文の尾に「確認不能の一覧 ／ 出典一覧 ／ 免責（本レポートは投資助言ではなく、人の最終判断のための材料です）」、`状態=レポート済`（無ければ Complete グループの選択肢）、`実行メモ` に完了時刻と件数
9. **通知**: 本文の頭の `@利用者` の後に「判断待ち n件（`判断` DB の 判断待ち（自分）ビューへのリンク）」

## 6. 目的別の統合と完了条件（§4）

### 6.1 スクリーニング

```
## 統合
一覧（≤ ウォッチ上限）:
| コード | 銘柄 | 残した条件（通過した観点） | 根拠（出典） | 前回との入替 |
落とした主な銘柄と理由（1行ずつ、最大10）
既判断（残す済／落とす済で再質問しない銘柄。件数と例）
```

候補の作り方: 各取得系観点の候補集合（`寄与=有利` の銘柄）の **和集合** → 観点「制約と既判断」で `見ない領域`（`sector` 文字列一致。`sector` が空の銘柄は判定 `確認不能` で除外しない）・既判断（同じ利用者の `判断` で `最終判断` ∈ {落とす, 見送り, 見送る} が 90 日以内、または `残す` あり）・`ウォッチ上限` を当てる → 一覧。`残す` 済の銘柄が今回落ちたら「入替」に書く。

- 判断材料の完了: 全有効観点の節がある（確認不能でも節はある）／一覧の各行に根拠と出典／おすすめ文・禁止語なし／件数 ≤ ウォッチ上限
- 学び材料の完了: 一覧の各銘柄に判断行（`AIの結論=通過`、`観点別寄与`、`AIの一言`＝残した条件、`適用ルール`）。銘柄行が無ければ `銘柄` に作る（`銘柄名`・`証券コード`。`市場` は書かない）。既判断の銘柄には作らない

### 6.2 企業分析

```
## 統合
事実（出典・基準日）／計算（式）／推論 を分けて各≤5行
買わない理由3つ（反証の節から。推論より先に置く）
推論: 有利寄り | 中立 | 回避寄り（既定: 不利 ≥ 有利 → 回避寄り／有利が過半かつ反証が軽い → 有利寄り／他 → 中立。観点ルールで上書き可）
確信度: 高 | 中 | 低（確認不能の観点が2つ以上 or 寄与が割れる → 低）
次に確認する日: YYYY-MM-DD（既定 5営業日後）
```

- 判断材料の完了: 全有効観点の節／反証が推論の前／`確認不能` が残る／`買う` なし
- 学び材料の完了: 判断行 1（`AIの結論` ∈ 有利寄り/中立/回避寄り/確認不能、`観点別寄与`、`AIの一言`（買わない理由の筆頭）、`確信度`、`反証条件`、`次回確認日`、`適用ルール`）

### 6.3 投資判断（売買計画）

エントリー帯: ルールの基準に対する条件（例「25日線から -5%〜0%」）。価格の値は書かない

### 6.4 変化なし（繰り返し・再確認）

統合は「変化なし（前回 <リンク>）。次回確認日 …」。判断行なし。`変化=なし`。開いている判断の `次回確認日` を同じ間隔で先送りする。

## 7. 変化の判定（§3.3）

| 判定 | 条件 |
| --- | --- |
| 初回 | 同じ利用者・目的・銘柄で `レポート済` の前回タスクがない |
| なし | 前回の統合節と比べて、各観点の寄与が同じ かつ 新しい開示（開示系の観点）がない かつ スクリーニングでは一覧の構成が同じ |
| あり | それ以外 |

`なし` のとき: 各観点の節は「前回（リンク）と差分なし」の 1 行でよい。

## 8. 自己検査（統合を書く前と仕上げの前。`guardrails.md` §8）

- 禁止語（`買う` `買い` `買い推奨` `今すぐ` `必ず` `絶対` `爆益` `急騰確実`）が本文・`AIの一言`・`要約` にない。例外は「買う条件」「買わない理由」「人の最終判断＝買う」の引用だけ
- personal-only の値（株価・出来高・RSI・PER・PBR・利回り・信用残高・倍率の数値）が本文・事実台帳・列にない。成立／未成立と確認先だけ
- 出典 URL と基準日のない数値がない（無ければ `確認不能`）
- `判断.最終判断`・`判断メモ` を書いていない。`ルール.状態` を `発効`・`棄却` にしていない。`分析観点`・`参照資産` を書いていない
- 節の見出し `## 観点: X` が `分析観点.観点名` と一致。`完了観点` と節の数が一致
- 各観点の取得が `取得上限`・`項目=`・`期間=` の範囲内（`limit` なし・全表読みなし）
- リポジトリを変更していない。PR・Slack など Notion 以外へ書いていない。シークレット値を出力していない
