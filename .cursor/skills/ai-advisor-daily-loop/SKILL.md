# 日次ループ（日次タスク → 日次レポート）

Automation「AI専属アナリスト｜日次ループ」の本体手順。人間が `日次タスク` の起動列を埋めた瞬間が「仕事の付与」であり、このスキルはそれを拾って **目的別の完了条件を満たす `日次レポート`** を書くところまでを担う。人間の最終判断・ルール発効は担わない。

## 0. 最初に読むもの（毎回）

1. `docs/ai-advisor/guardrails.md` — 絶対ルール。以下の要約は抜粋にすぎない。
2. `docs/ai-advisor/notion-schema.md` — DB ID・ビュー URL・プロパティ名・状態値・実行パラメータ（観点ごとの上限）の正本。**ID が `TODO` の DB には書き込まない。**
3. `docs/ai-advisor/reference-data.md` — 参照データ源（kabulab 公開 API）、出典タグ（何を Notion に書けるか）、`分析観点` のスライス定義と既定カタログ。
4. Notion MCP の `fetch` で `TASKS` / `REPORTS` / `KNOWLEDGE` / `RULES` / `EXPERTS`（あれば `AXES`）のデータソースを取得し、プロパティ名がスキーマ表と一致することを確認する（不一致は実行サマリーに書き、該当 DB への書き込みを止める）。`fetch` は **スキーマ確認のため** に使い、行データをここで読み込まない。

絶対ルール（抜粋）:

- 本文とプロパティに `買う` `今すぐ買う` `おすすめ` `推奨` `必ず` `確実` を書かない。AI所見は `有利寄り` / `中立` / `回避寄り`、材料分類は `監視のみ` / `押し目待ち` / `見送り`。
- `状態=発効` 以外のルールは読まない・使わない。
- `最終判断` 行を作らない。`ルール` の `状態` を変えない。注文しない。
- 取れない数字は `確認不能`。捏造しない。事実 / 計算 / 推論 を分ける。
- **personal-only（Yahoo / JPX / 日証金 由来: 株価・PER/PBR・RSI 等・スコア・市場区分・JPX 業種・信用残高）の値を Notion に書かない。みんかぶ由来の掲載文はどこにも書かない。** 業種は EDINET 由来の 33 業種だけ。
- **データ全体を読まない。** 分析観点を 1 つずつ、宣言されたスライス（エンドポイント / フィールド / 銘柄 / 期間 / 件数上限）だけ取り、要約を Notion に書いてから次へ。`LIMIT` なしの取得・全表読み・全ページ送りをしない。
- リポジトリを変更しない。PR を作らない。Slack 等へ投稿しない。シークレット値を出力しない。

## 1. 実行環境の確認

- Notion MCP のツール（`notion-fetch`, `notion-query-data-sources`, `notion-create-pages`, `notion-update-page`, `notion-create-comment`）が使えることを確認する。使えない場合だけ、`docs/ai-advisor/notion-schema.md` §6 の REST フォールバック（`NOTION_TOKEN`）を使う。どちらも使えなければ、何も書かずに実行サマリーへ「Notion に接続できない」と書いて終了する。
- 現在時刻を JST で持つ（`TZ=Asia/Tokyo date +%F`）。`対象日` の既定値はこの日付。

## 2. 対象行の取得

1. `TASKS` のビュー「自動化_実行待ち」を `notion-query-data-sources`（`mode: "view"`, `page_size: MAX_TASKS_PER_RUN`）で **1 ページ目だけ** 読む。ビュー URL が `TODO` なら、rows モードで `状態 = READY_STATUS` かつ `目的` 非空 かつ `ルール` 非空 をフィルタし `limit: MAX_TASKS_PER_RUN` を付ける。
2. `対象日` 昇順 → 作成日時 昇順に並べ、先頭から `MAX_TASKS_PER_RUN` 件だけを今回の対象にする。残り（`has_more`）は数だけ実行サマリーに「次回」と書き、読まない。
3. `状態 = RUNNING_STATUS` の行が `STALE_RUNNING_HOURS` を超えて残っていれば、触らずに実行サマリーで警告する（人間が戻す）。
4. 対象が 0 件なら、何も書かずに実行サマリー「実行待ち 0 件」で終了する。

## 3. 行ごとの前検査（起動必須列）

対象行ごとに、以下を **すべて** 満たすか確かめる。1つでも欠ければ `状態 = INSUFFICIENT_STATUS` にし、`notion-create-comment` で欠けている項目を箇条書きでコメントして、この行は終了（レポートは作らない）。

| 検査 | 条件 | 欠けたときのコメント例 |
| --- | --- | --- |
| 目的 | `目的` が 3 値のいずれか | 「目的が空です」 |
| ルール | `ルール` に 1 行以上。**すべて** `状態=発効` で、`対象目的` に `目的` を含む | 「ルール〈ID〉は 発効 ではありません / 対象目的に〈目的〉が含まれていません」 |
| 対象日 | 空なら当日(JST)を入れる（これは AI が埋めてよい唯一の起動列） | — |
| 対象銘柄 | `目的` が `企業分析` / `投資判断（売買計画）` なら 1 行以上 | 「企業分析には対象銘柄が必要です」 |
| 専属の解決 | 次の順で 1 行に決める: ① タスクの `専属エキスパート` → ② `利用者` が `オーナー` の `EXPERTS` 行 → ③ ルールの `専属エキスパート` → ④ ルールの `オーナー` が `オーナー` の `EXPERTS` 行。決まらなければ不足 | 「専属エキスパートが決まりません」 |
| 制約4項目 | 解決した専属行の `投資期間` / `1銘柄あたり金額` / `許容損失` / `見ない領域` がすべて非空 | 「制約〈項目名〉が空です。空の制約のままスクリーニングしません」 |
| 他人のルール | ルールが `種別=個人` のとき、その `オーナー`（または `利用者`）が解決した専属の `オーナー` と一致する。`共通テンプレ` は誰でも可 | 「他メンバーの個人ルールは適用できません」 |

`利用者` が空なのは正常。②で解決できなければ③④で補完する。

## 4. ロック

1. `notion-update-page` で `状態 = RUNNING_STATUS`、`完了条件` に §6 の完了条件文、`専属エキスパート` に解決した行、必要なら `対象日` を書く。
2. 直後に同じ行を再取得し、`状態` が自分の書いた `RUNNING_STATUS` であることを確認する。別の実行に先に取られていた（再取得前から `実行中` だった、または `日次レポート` が既に付いている）場合はこの行をスキップし、実行サマリーに書く。

## 5. 読む順（計画書 §4.4。設定だけ先に、データは観点ごとに）

ここで読むのは **設定と文脈だけ**。参照データ（kabulab API・一次情報・過去レポート本文・知識）はまだ読まない — §6 の観点ループで、観点ごとのスライスとして読む。

1. 当該 `日次タスク`（目的 / ルール / 利用者 / 対象銘柄 / 対象日）— その 1 ページ
2. 解決した `専属エキスパート`（制約4項目、`低確信度のサイズ`、`ウォッチ上限`、`既定の目的`）— その 1 ページ
3. 関係づいた `ルール`（`状態=発効`）— その 1 ページ。本文は **目的に対応する見出し**（スクリーニング: 1・2 / 企業分析: 2・3 / 投資判断: 4・5）と「6 評価・振り返りの見方」だけを読む
4. 観点の一覧を決める: ルールに `分析観点` relation があれば、その観点行を `順序` 昇順に **最大 `MAX_AXES_PER_TASK` 件**（各 1 ページ）。無ければ `AXES` のビュー「自動化_有効観点」を `対象目的` で絞って 1 ページ目（`page_size: MAX_AXES_PER_TASK`）。`AXES` も未配線なら `docs/ai-advisor/reference-data.md` §4.3 の既定カタログのうち、この目的の観点を順に使う
5. 過去レポートの **参照だけ** を取る: `REPORTS` を rows モードで `目的` と `適用ルール` と（企業分析・投資判断なら）`対象銘柄` でフィルタ、`sort: 対象日 desc`, `limit: PAST_REPORTS_TO_READ`。ここでは **タイトル・URL・`変化`・`完了` の 4 列だけ** を持ち、本文は観点ループで必要になった 1 件だけ読む
6. `docs/ai-advisor/guardrails.md`（表現と免責）

読まないもの: 未発効ルール、他メンバーの個人ルール、`知識` / `日次レポート` DB の総なめ、公開 API の全件、リポジトリ内の既存リサーチ資産（`0001_…` 〜 `0016_…` 配下）、チャット履歴、Automation の Memories。

## 6. 目的別の仕事と完了条件

| 目的 | 完了条件（`完了条件` 列にコピーする文） | 本文テンプレ |
| --- | --- | --- |
| スクリーニング | 銘柄一覧とその根拠（残した条件、落ちた理由、出典。おすすめ文なし） | §6.1 |
| 企業分析 | 分析結果（事実／計算／推論分離、反証先行、確認不能を残す） | §6.2 |
| 投資判断（売買計画） | その銘柄の売買タイミング等（IF-THEN、エントリー帯、破綻条件、サイズ提案。発注指示ではない） | §6.3 |

### 6.0 観点ループ（1 観点ずつ: 取る → 要約を書く → 捨てる）

レポートの本文は、観点ごとの要約を積み上げて作る。**まずレポート行を空で作り**、観点を 1 つ終えるごとに本文へ節を追記する（途中で落ちても書いた分は Notion に残る）。

0. **レポート行を先に作る**: `REPORTS` に §7-1 のプロパティで 1 行（本文は見出し「0. 適用ルールと制約」だけ、`完了=__NO__`）。`日次タスク.日次レポート` に紐づける。
1. **観点を 1 つ取り出す**（§5-4 の順）。その観点の **スライス** を確認する: `データ源` / `エンドポイント` / `フィールド` / `銘柄範囲` / `期間` / `件数上限` / `出典タグ`。上限は観点の値と `docs/ai-advisor/notion-schema.md` §5（`MAX_ROWS_PER_AXIS` / `MAX_FIELDS_PER_AXIS` / `MAX_STOCKS_PER_AXIS`）の **小さい方**。
2. **スライスだけ取得する**:
   - kabulab 公開 API（`docs/ai-advisor/reference-data.md` §2）: `limit` を必ず付け、`{code}` はタスクの対象銘柄（または前観点で残った候補）だけ。レスポンスは `フィールド` の列だけ残し、他は捨てる。
   - 一次情報（EDINET / TDnet / 会社 IR）: 文書は観点が指す 1〜2 本、読む節は観点の問いに要る節だけ。
   - Notion（過去レポート・知識）: `fetch` で **1 ページ**、または rows モードで `limit` 付き。`知識` は `銘柄` と `基準日` で絞り `limit: MAX_KNOWLEDGE_PER_REPORT_REVIEW`。
   - `personal-only`（B1〜B4）は、その観点が条件判定に必要とするときだけ取り、**値は Notion に書かない**（条件の成否と kabulab URL だけ）。
   - 取れない・上限で足りない → その観点は `確認不能（理由）` で確定し、次へ。
3. **要約を書く**（`MAX_SUMMARY_CHARS_PER_AXIS` 以内、数字は出典＋基準日つきで `MAX_FACTS_PER_AXIS` 個まで、残りは「他に n 件」）: `notion-update-page`（`insert_content`, `position: end`）でレポート本文に「観点: 〈観点名〉」の節を追記する。同時に、要約の根拠になった事実を `KNOWLEDGE` に **最大 `MAX_KNOWLEDGE_PER_AXIS` 行**（`タイトル`, `種別`（事実/計算/推論/不明）, `共有範囲`, `銘柄`, `出典`(元の EDINET / TDnet / IR の URL), `基準日`, `データ品質`, `一過性`, `元タスク`, `オーナー`）。同じ銘柄・同じ基準日・同じ内容の `知識` が既にあれば作らず参照する。`personal-only` / `no-store` の事実は `知識` にも書かない。
4. **捨てる**: 以後この観点の生データを参照しない。次の観点は、前の観点の **要約**（Notion に書いた文）だけを前提にする。再取得・再掲をしない。
5. `MAX_AXES_PER_TASK` に達したら残りの観点は読まず、本文に「未処理の観点: 〈名〉…（観点数の上限）」と書く。
6. すべての観点を終えたら §6.1〜6.3 の **結論節**（一覧表 / 買わない理由 / 推論 / IF-THEN / 分類 など）を、観点要約だけから書いて追記し、`完了` と `変化` を確定する（§7）。

一次情報源の優先: EDINET（有報・四半期）→ TDnet / 会社 IR（決算短信・適時開示）→ 会社サイト。二次情報（ニュース・まとめサイト）は補助。数字は一次情報で裏取りし、取れなければ `確認不能`。株価・出来高・指標は Yahoo / JPX 由来なので Notion に値を書かない（`docs/ai-advisor/reference-data.md` §1）。

本文の共通構造: 「0. 適用ルールと制約」→「観点: …」節 ×N（§6.0 で追記済み）→ 目的別の **結論節**（以下）→ 免責文 1 行。結論節は観点要約だけから書く。

### 6.1 スクリーニング（既定観点 S1〜S4）

結論節（順序固定）:

1. **一覧表** — 列: `証券コード` / `名称` / `残した条件`（ルールのどの基準を満たしたか） / `根拠（出典・基準日）` / `落ちていない理由`。件数は `ウォッチ上限` 以内。`personal-only` 条件（PER・RSI 等）は「条件〈…〉を満たす（kabulab で本人確認: URL）」と書き、**数値を書かない**
2. **落とした銘柄と理由**（1 行ずつ。見ない領域に該当したものも含む。上限を超えた分は「他に n 銘柄」）
3. **確認不能**（取れなかった数字・確認できなかった条件・観点の上限で見られなかったもの）
4. **前回レポートからの入替**（新規 / 消滅 / 継続。前回がなければ「初回」。前回レポートは §5-5 の参照から **1 件だけ** 本文の一覧表を読む）
5. 免責文 1 行

一覧の銘柄は `STOCKS` に無ければ作ってよい（`名称`, `証券コード`, `状態=ウォッチ候補`。`市場` は書かない）。`変化`: 前回一覧と入替がなければ `なし`、あれば `あり`。`なし` のときは本文冒頭に「前回から変化なし」と書き、判断を求める文を書かない。

### 6.2 企業分析（既定観点 C1〜C5）

結論節（順序固定。**「買わない理由」は「推論」より前に置く**）:

1. **制約との一致**（投資期間・1銘柄あたり金額・許容損失・見ない領域に照らして対象として適格か）
2. **事実の要約**（観点要約から。出典 URL・基準日つき。売上・利益・受注・開示など、ルール「3 企業分析で必ず見る項目」に沿う）
3. **計算**（成長率・比率など。計算式と入力値を書く。一過性利益は分けて減点として明示。バリュエーション（PER/PBR）は `personal-only` なので数値を書かず、「kabulab で本人確認」）
4. **買わない理由 3 つ**（反証。先に書く）
5. **推論** — AI所見: `有利寄り` / `中立` / `回避寄り` と、その条件文
6. **確認不能**
7. **次に確認する日**（決算発表日・開示予定など。不明なら `確認不能`）
8. 免責文 1 行

`変化`: 前回の企業分析レポート（§5-5 の参照から 1 件、「推論」節だけ読む）から所見が変わっていなければ `なし`。

### 6.3 投資判断（売買計画）（既定観点 I1〜I4）

前提: 同じ銘柄の `企業分析` レポート（完了）があること（観点 I1 で **1 件だけ** 読む）。無ければ本文 1 節で「企業分析レポートなし」と明記し、要約を最小限にする（新たな企業分析はここでは行わない）。

結論節（順序固定）:

1. **企業分析の要約または関係**（元レポートへのリンク。AI所見）
2. **買わない理由 3 つ**（反証先行）
3. **IF-THEN**（材料として成立する条件 / 見送る条件。ルール「4 エントリー・損切り・利確・破綻」に沿う）
4. **エントリー帯 / 破綻条件 / サイズ提案** — 「これは発注指示ではありません」と明記。帯と破綻条件は **式**（「25 日線 −3%」「直近安値割れ」）で書き、価格の数値は書かない（`personal-only`）。サイズはルール「5 ポジションサイズとRR」と制約（1銘柄あたり金額・許容損失）から算出し、式を書く
5. **確信度**（高 / 中 / 低 とその理由。`低` なら通常サイズを提案せず `低確信度のサイズ` を使う）
6. **分類**: `監視のみ` / `押し目待ち` / `見送り`
7. **人間への操作** — 「`最終判断`（買う／待つ／見送る）を 1 行お書きください。」（AI は `最終判断` 行を作らない）
8. 免責文 1 行

## 7. `日次レポート` の確定と `日次タスク` の更新

1. レポート行は §6.0-0 で先に作ってある。作成時のプロパティ（`notion-create-pages`, `parent.data_source_id`）:
   - `レポート名`: `YYYY-MM-DD 目的`（企業分析・投資判断は末尾に ` 証券コード 名称`）
   - `利用者`: タスクからコピー（空なら空のまま）
   - `目的`, `対象日`: タスクと同じ
   - `元タスク`: 当該タスク
   - `適用ルール`: 実行時に読んだ `発効` 行（**バージョン固定。後で差し替えない**）
   - `対象銘柄`: 企業分析・投資判断は対象銘柄（スクリーニングは結論で一覧が決まってから追記）
   - `完了`: `__NO__`（結論節を書き終えたら確定）
2. 結論節を書き終えたら `notion-update-page`（`update_properties`）で確定する: `根拠知識`（観点ループで作成・参照した `知識` 行）、`対象銘柄`（スクリーニングは一覧の全銘柄）、`完了`（完了条件を満たしたら `__YES__`、満たせなければ `__NO__`）、`変化`（`あり` / `なし`）。
3. `日次タスク` を更新: `状態` を
   - 完了条件を満たした → `REPORTED_STATUS`
   - 満たせなかった（一次情報が取れず本文の大半が `確認不能` など） → `INSUFFICIENT_STATUS` にし、コメントで「完了条件未達: 〈理由〉」と書く。レポート行は `完了=__NO__` のまま残す（数字は後で書き換えない。翌日の新しいタスクで再実行する）
4. 1 タスク 1 レポート。既に `日次レポート` が付いている行にはレポートを追加しない。

## 8. 自己検査（各レポートの保存前）

`docs/ai-advisor/guardrails.md` §8 を実施する。特に:

- 禁止語検索（`買う` `今すぐ買う` `買い推奨` `売り推奨` `おすすめ` `推奨` `必ず` `確実`）。見つかったら言い換える。§6.3-7 の「最終判断（買う／待つ／見送る）」の選択肢列挙だけは例外
- 数字ごとに出典 URL＋基準日、または `確認不能`
- 企業分析・投資判断で「買わない理由 3 つ」が推論より前にある
- `適用ルール` が `状態=発効` の行を指す
- `最終判断` 行を作っていない、`ルール` の `状態` を変えていない、リポジトリを変えていない
- personal-only の値（株価・PER/PBR・RSI・スコア・市場区分・JPX 業種・信用残高）と、みんかぶ由来の掲載文が本文・プロパティ・`知識`・コメントに出ていない
- 各観点の取得が宣言スライスと上限の範囲内だった（`limit` なしの取得・全表読み・全ページ送りをしていない）。各観点要約が `MAX_SUMMARY_CHARS_PER_AXIS` 以内

## 9. 実行サマリー（Automation の実行ログとして返す）

```
日次ループ 実行サマリー（JST YYYY-MM-DD HH:MM）
- 実行待ち: N 件 / 今回処理: M 件 / 次回へ: K 件
- 行ごと: 〈タスク名〉 → レポート済｜不足（理由）｜スキップ（理由）〈レポートURL〉
  - 観点: 〈観点名〉 取得 n 行 / 要約 m 字 / 知識 k 行 … （観点ごとに 1 行。personal-only は「判定のみ」と記す）
- 確認不能: 〈銘柄・項目〉…（観点の上限によるものは「上限」と明記）
- 観点の上限見直し提案: 〈観点名〉 …（人間が定義を直す。自動化は変えない）
- 警告: 実行中のまま N 時間の行 / スキーマ不一致 / 未配線 DB …
```

Slack や PR には出さない。Notion のコメント以外に通知を作らない。

## 10. 未配線・スキーマ不一致のときの振る舞い

- `docs/ai-advisor/notion-schema.md` で `TASKS` / `REPORTS` / `KNOWLEDGE` のいずれかの ID が `TODO` → 読み取りテスト（`fetch` で親ページ配下の DB 名を列挙）だけ行い、「未配線: 〈DB キー〉」を実行サマリーに書いて終了する。書き込みはしない。
- プロパティ名が一致しない → その DB への書き込みを止め、「スキーマ不一致: 〈DB〉.〈期待名〉 が見つからない（候補: …）」を書いて終了する。
