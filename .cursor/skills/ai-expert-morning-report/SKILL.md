# 朝レポート（仕事 → 切片の節 → 統合 → 判断行 → 円帯 POST）

正本は計画書（`docs/ai-expert-plan.md` が GitHub に無い間は Project store）。この文書は **手順どおりに実行するための操作手引き**。周辺文書:

- `docs/ai-expert/guardrails.md`
- `docs/ai-expert/notion-schema.md`
- `docs/ai-expert/reference-data.md`
- `references/jp-holidays.md`

旧 8DB（`docs/ai-advisor/`・`ai-advisor-*`）には **読み書きしない**。

## 0. 役割と前提（毎回）

- 役割: 自己成長するあなただけのAI投資エージェント。**投資助言をしない。人の最終判断を代行しない。発注しない。** 日本株。目的は `スクリーニング` と `売買判断` のみ。
- モデル: ダッシュボードは **Grok 4.6**。
- 固定値: 親ページ `AI投資エージェント`（https://app.notion.com/p/3ddd74ff84cd81789abbcf86708626c0）。5DB（`エージェント` `ルール` `仕事` `判断` `振り返り`）は親の子を **名前で解決**。ID は `docs/ai-expert/notion-schema.md` §1（2026-09-16 照合済み）。食い違えば **名前解決を優先**。
- **状態列は select**（Notion の status 型ではない）。フィルタ・更新は `select` / `select_equals`。`status`・`status_is`・`is_group` は使わない（旧 8DB 専用）。語彙: 仕事 `未着手` / `不足` / `実行中` / `レポート済`。エージェント `設定中` / `運用中` / `休止`。ルール `草案` / `発効` / `失効` / `棄却`。
- **`判断ID` は title**（text ではない）。判断行の新規は title に一意キーを書く。CF 円帯の `notion_decision_id` もこのタイトル文字列。
- 時刻: JST。実行ID `YYYYMMDD-HHMM-朝レポート`。
- 営業日: 月〜金 かつ `references/jp-holidays.md` の祝日・12/31〜1/3 でない日。判定できない日は営業日とみなす。
- 無人実行。同時 1 インスタンス。ロックは `状態=実行中`＋`実行メモ` の実行ID。
- 文脈予算: 切片ごとに切ってから読む。1 切片は要約 ≤600 字。書いたら捨てる。1 ラン: 仕事 10 行、軽 8 / 重 1。
- 共有面は Notion のみ。円は `AI_EXPERT_YEN_API_URL` + `AI_EXPERT_YEN_STORE_SECRET`（値は出力しない）。

## 1. 起動時に読むもの（データはまだ読まない）

1. 上記 4 文書
2. 親ページ → 5DB の名前解決とプロパティ名確認（ここでは行データを読まない）。未解決 DB があれば書き込みせず終了
3. 当日（JST）と営業日判定、実行ID
4. 円帯 API の URL が空なら円 POST をスキップする前提を実行サマリーに書く（Notion は進める）

## 2. 起動条件・解決規則

### 2.1 仕事 1 行に対する読み順

1. `仕事` の行（目的・対象コード・方向・利用者・対象日・適用ルール・完了切片・状態・実行メモ・繰り返し）
2. **エージェント**: `利用者` で `エージェント` を `オーナー` 一致検索（rows、`limit: 1`）。無ければ `WebユーザーID` では引かない（person の自動推定禁止）。`状態=運用中` でなければ不足。読む列: 制約4・ウォッチコード・低確信度のサイズ・WebユーザーID・ルール公開
3. **ルール**: 仕事の `適用ルール` が既にあり `発効` ならそれを固定（変えない）。空なら「`オーナー`＝利用者 かつ `目的` ∋ 仕事の目的 かつ `状態=発効`」を `発効日` 降順 1 行 → 無ければ「`オーナー` 空（共通）」同条件 1 行 → 無ければ `RULE_UNRESOLVED`。他人の発効は **適用しない**（Web で読めるだけ）
4. 目的が `スクリーニング` でも `売買判断` でもない → `NO_PURPOSE`（企業分析は受けない）
5. 売買判断で `対象コード` 空 → `NO_STOCK`。コードが 4 桁に正規化できない → `STOCK_UNRESOLVED`
6. 前回仕事（同じ利用者・目的・対象コードで `レポート済` の最新 1。`## 統合` 節だけ）、過去判断（同じ利用者×コード、20 行。列だけ）
7. 固定切片（`reference-data.md` §4。目的別セット。`完了切片` にある名前は飛ばす）

`適用ルール` は実行開始時に relation で固定し、以後変えない。

### 2.2 不足コード

| コード | 意味 |
| --- | --- |
| `NO_PURPOSE` | `目的` が空、またはスクリーニング／売買判断以外 |
| `NO_STOCK` | 売買判断で `対象コード` が空 |
| `STOCK_UNRESOLVED` | 証券コードに解決できない |
| `NO_AGENT` | 利用者のエージェント行がない（作らない。Web オンボーディングの仕事） |
| `EXPERT_NOT_ACTIVE` | エージェントが `運用中` でない |
| `CONSTRAINT_EMPTY:<列名>` | 制約4（`投資期間` `1銘柄あたり金額` `許容損失` `見ない領域`）のどれかが空 |
| `RULE_UNRESOLVED` | 発効ルールが個人にも共通にもない |
| `RULE_NOT_ACTIVE` | 明示されたルールが発効でない |
| `WRITE_FAILED` | Notion 書き込みが 2 回再試行しても失敗 |

`不足` の行は毎ラン再評価し、揃っていれば `未着手` に戻す。切片の到達不能は不足にしない（その切片 `確認不能`）。

銘柄名: IR / 有報の `name`、無ければ凍結 `stocks.json` を 1 コードだけ。`market` は書かない。

## 3. ルール整理（冪等）

1. `ルール` を `状態=発効` で読む（`limit: 100`。列: ルール名・オーナー・目的・方向・前バージョン・発効日・作成日時）
2. `オーナー`×系（`前バージョン` を辿る）でまとめ、同系に `発効` が 2 行以上あれば、`発効日`（空なら作成日時）が最新以外を `状態=失効`、`変更要約` 末尾に `（自動失効 実行ID）`
3. `発効` で `発効日` が空なら当日を補完

これ以外に `ルール.状態` を変えない（`発効`・`棄却` にしない）。

## 4. 準備（冪等。休場日は (a) を行わない）

| 手順 | 条件 | 書く |
| --- | --- | --- |
| (a) 繰り返し展開 | 営業日。`繰り返し=毎営業日` かつ `対象日`＝前営業日 かつ `状態=レポート済`。当日分が無い | 新行: `対象日`=当日、`状態`=未着手、`起票元=繰り返し`、`実行メモ`=`複製元:<前行URL>` |
| (b) 連鎖 | `最終判断=残す` かつ同じコードの未処理の売買判断仕事が無い | 新行: `目的=売買判断`、`対象コード`=判断.コード、方向はウォッチまたはルール、`起票元=連鎖` |
| (c) 再確認 | `最終判断=待つ` かつ次回が当日以前（次回確認の記載が追跡メモ／仕事に無ければ翌営業日とみなす） | 同じ方向で再実行仕事。`変化なし` なら後で判断行を作らない |
| (d) 落とす／見送る | 90 日以内の `落とす` `見送る` コードはスクリーニング再提示しない | 準備では起票しない |
| (e) `買う` / `売る` | 新しい仕事は作らない。夕が追跡する | — |
| (f) 不足の再評価 | `状態=不足`（または `実行メモ` が `不足:`） | 揃えば `未着手` |
| (g) ウォッチ起票 | 実行待ちが 0 で、運用中エージェントにウォッチコードがあり、当日のスクリーニングが無い | 1 人 1 行まで。`目的=スクリーニング`、`起票元=繰り返し`、`対象コード` 空 |

(b)(c) の `判断` は `limit: 50`。人が選んだ語を実行しているだけで、AI が勝手に仕事を増やしているのではない。

## 5. 実行（仕事ごと）

対象: ビュー「自動化_実行待ち」があれば 1 ページ目。無ければ rows。**自分で絞る**:

- `対象日` 空または ≤ 当日。未来日は除く
- `未着手`（`不足:` 先頭の行は除く）、または `実行中` かつ `完了切片` 非空
- 仕事名が `テンプレート｜` または `例｜` で始まる行は除く
- `対象日` 昇順、**10 行で打ち切り**

1. **ロック**: `状態=実行中`、`実行メモ` 先頭に実行ID。60 分無進捗なら引き継ぎ。
2. **起動条件**（§2）。不足なら書いて次へ。
3. **適用ルール** を固定。
4. **本文の頭**（初回のみ）:

   ```
   作成中（0/m 切片）
   @利用者 ／ 判断待ち: 統合後に記入
   適用ルール: <ルール名>
   制約との一致: 投資期間 … ／ 1銘柄あたり金額 … ／ 許容損失 … ／ 見ない領域 …
   帯の円は本人画面で確認。ここでは条件の成立／未成立だけ。
   変化: （統合で確定）
   ```

5. **切片ループ**（目的別セット。`重` は 1 で打ち切り、`軽` は 8。`完了切片` は飛ばす）
   1. `reference-data.md` §4 の取得形。jss-api MCP が同じ切片を返せるならそれを優先（limit/項目/期間を守る）
   2. 失敗 → 1 回再試行 → `確認不能`
   3. 本文末尾に節を追記:

      ```
      ## <切片名>
      要約: （≤600字。事実／計算／推論を分ける。personal-only は成立／未成立のみ）
      寄与: <有利|中立|不利|確認不能> — <理由1行>
      根拠: <経路> <URL> 取得 <YYYY-MM-DD HH:MM JST> 読んだ件数 <n>
      確認不能: （無ければ「なし」）
      ```

      見出しの切片名は固定名と一致（地合い / 受注 / 海外 / 開示の流れ / 一次情報 / 優待 / 価格条件 / 需給 / 直近開示 / サイズと破綻 / 反証 / 制約と既判断）
   4. `完了切片` にカンマ区切りで追加。本文先頭の `作成中（k/m 切片）` を更新
   5. **捨てる**: `rm -f /tmp/slice-*`。以後参照しない
   6. 上限なら `実行中` のまま終える
6. **統合**（全予定切片が完了切片にある場合のみ）。外部データを再取得しない。自己検査（guardrails §7）
7. **判断行**: 既存（`元仕事`×`コード`）があれば作らない。`変化=なし` なら作らない。`判断ID` は **title**（例 `YYYY-MM-DD 目的 コード`）。`最終判断` `判断メモ` は空。`円帯キー` に UUID（数値ではない）
8. **円帯 POST**: 円帯がある判断だけ、`WebユーザーID` を `user_id` にして 1 回 POST（`reference-data.md` §5）。失敗しても Notion は完了、`YEN_STORE_FAILED`。既存は上書きしない
9. **仕上げ**: `仕事名`（`YYYY-MM-DD 目的 [コード]`）、`要約` ≤200 字、`変化`、本文先頭の作成中を外す、尾に確認不能一覧／出典／「本レポートは投資助言ではなく、人の最終判断のための材料です。」、`状態=レポート済`

## 6. 目的別の統合

### 6.1 スクリーニング

```
## 統合
一覧（ウォッチコードと通過銘柄。最大 30）:
| コード | 銘柄 | 残した条件 | 根拠（出典） | 前回との入替 |
落とした主な銘柄と理由（1行ずつ、最大10）
既判断（落とす済／見送る済で 90 日再提示しない件数と例）
```

候補: 受注・海外などで `寄与=有利` の和集合 → 見ない領域（EDINET 33 業種の言葉。sector 空は除外しない）・既判断 90 日・ウォッチ上限。おすすめ文なし。

- 学び材料: 残した銘柄に判断行（`AIの結論=通過`）。落とした理由は `入らない理由` に 1 行。既判断には作らない

### 6.2 売買判断

```
## 統合
入らない理由 3 つ（反証の節から。推論より先）
IF-THEN: 買う条件 / 売る条件 / 見送り条件 / 破綻条件（ルールの条件文。指示ではない）
現在の位置: 価格条件 成立|未成立（値は転記しない。基準日）／需給 成立|未成立
サイズ方針: 式 min(1銘柄あたり金額, 許容損失 ÷ 破綻幅)。低確信度は「通常の半分」
確信度: 高|中|低
分類: 条件成立 | 押し目待ち | 戻り待ち | 監視のみ | 見送り | 確認不能
  既定: 価格条件 成立 かつ 反証 ≠ 不利 → 条件成立（方向列で買い／売り）／未成立かつ買い方向 → 押し目待ち／売り方向で戻りを待つ → 戻り待ち／反証=不利 → 見送り／一次情報 確認不能 → 監視のみ
```

「今すぐ」は使わない。判断行 1（`AIの結論`＝分類と同じ語彙）。

### 6.3 変化なし

統合は「変化なし（前回 <リンク>）」。判断行なし。`変化=なし`。

## 7. 変化の判定

| 判定 | 条件 |
| --- | --- |
| 初回 | 同じ利用者・目的・コードで前回レポート済がない |
| なし | 前回の統合と比べて各切片の寄与が同じ かつ 新しい開示がない かつ スクリーニングでは一覧が同じ |
| あり | それ以外 |

## 8. 自己検査

`docs/ai-expert/guardrails.md` §7 を統合前・仕上げ前・円 POST 前に行う。

## 9. 実行サマリー

```

- 解決: 5DB 名前一致 ／ 状態名: … ／ 円帯 API: 設定済｜未設定
- 営業日: はい｜いいえ ／ ルール整理: 失効 n・発効日補完 n ／ 準備: 複製 n・連鎖 n・再確認 n・ウォッチ起票 n
- 実行待ち: N ／ 今回: M ／ 未処理: K
- 行ごと: 〈仕事名｜URL〉 → レポート済｜実行中（k/m）｜不足 <コード>

- 判断行: 作成 n（最終判断は空）／ 円 POST: 成功 n / 失敗 n / スキップ n

```
